# ADR 0013: Store slot boundaries as local wall-clock time plus zone

- Date: 2026-04-08
- Status: **proposed** — not agreed, not implemented
- Author: Gareth Owusu
- Related: ADR 0005, ADR 0011, HP-503

## Context

We store `bookings.starts_at` / `ends_at` as `timestamptz` (UTC). Bookable
slots, though, are defined in Europe/London local time, and what hirers care
about is "Tuesday 7pm", not an instant.

This has bitten us in recurring series. `recurring.occurrence_windows`
computes occurrences as first-occurrence-UTC + n weeks, so a series that
crosses a clock change is an hour out for every occurrence on the other
side of the change (HP-503). After the October 2025 change we had 23 series
showing 18:00 instead of 19:00; see
`docs/findings/bookings-hp503-dst-series-audit-2026-04.md`.

Fixing only the arithmetic (add weeks to the *local date*, then convert) is
easy, but:

- extending an existing series would produce times that don't match the
  already-materialised rows, and staff can't tell from the DB which rows were
  "meant" to be 19:00;
- reports and the caretaker sheet re-derive local time from UTC everywhere,
  with assorted helper functions, and two of them get it wrong for the
  changeover weekend.

## Proposal

Add to `bookings` (and use in `booking_series`):

- `local_date date`, `local_start time`, `local_end time`,
  `tz text NOT NULL DEFAULT 'Europe/London'`

…as the **source of truth for what was booked**, and keep `starts_at` /
`ends_at` as derived UTC instants (generated in application code, checked by a
nightly job) because the exclusion constraint (ADR 0009) and most queries need
real instants.

Occurrences of a series are generated by stepping `local_date`, so a club's
19:00 stays 19:00 all year.

## Open points

- Back-fill: for existing rows, which local time is "right"? For series we
  can use `booking_series.local_start_time`; for one-off bookings, the
  current UTC→local conversion is right by definition.
- Do we need `tz` at all? Every facility is in the UK, and
  `facilities.timezone` already exists (always 'Europe/London', never read).
  Gareth thinks a per-booking zone is cheap insurance; Hannah thought it was
  YAGNI and we should just read the facility's. (Hannah has since left.)
- Fold handling on the October changeover night (01:00–02:00 happens twice).
  No space is open then, so we'd reject those times outright. That's an
  assumption, see `docs/bookings/time-and-dst.md`.
- Migration is area D's; needs a slot in the migration plan.

## Status

Discussed at the April 2026 tech catch-up; nobody objected, nobody signed it
off. Not started. Until it is, the workaround for HP-503 (split series at the
changeover) stays.
